# CursorManager

Менеджер системного курсора через именованные запросы состояния (`Show`/`Hide`), устойчивый к тому, что несколько источников одновременно хотят разное состояние курсора и снимают свои запросы в произвольном порядке.

## Проблема, которую решает

Наивные подходы к управлению курсором ломаются, как только в игре может быть открыто больше одного UI-окна одновременно:

- **Булев флаг** (`showCursor = true/false`) — второе открытое окно перезаписывает состояние первого; закрытие любого из них может скрыть курсор, даже если другое окно ещё открыто.
- **Счётчик открытых окон** (`openCount++`/`openCount--`) — не различает, *какое* окно давало запрос, поэтому не защищён от двойного `Hide` одного и того же окна (счётчик уйдёт в минус) и не даёт восстановить конкретное визуальное состояние (`CursorLockMode`), которое требовал именно последний активный запрос.
- **Стек** (`Stack<CursorState>`) — работает, только если окна закрываются строго в обратном порядке открытия. Открыли A, потом B, закрыли A (а не B) — стек этого не ожидает.

`CursorManager` хранит список активных запросов, ключом каждого из которых является `source` (обычно `this` вызывающего кода — так же, как в `FlagResolver`). Пока активен хотя бы один запрос "показать", курсор виден — независимо от порядка снятия остальных запросов, и независимо от того, сколько раз и в каком порядке источники обновляли своё состояние.

## API

| Метод | Назначение |
| --- | --- |
| `Show(source)` | Запрашивает видимый, разблокированный курсор (`CursorLockMode.None`, `Visible = true`) от имени `source`. |
| `Hide(source)` | Запрашивает скрытый и заблокированный курсор (`CursorLockMode.Locked`, `Visible = false`) от имени `source`. |
| `Release(source)` | Снимает запрос `source` и применяет состояние последнего тронутого из оставшихся активных запросов, либо `defaultState`/`EmergencyFallback`, если активных запросов не осталось. |
| `HasRequest(source)` | Есть ли у `source` сейчас активный запрос (`Show` или `Hide`, неважно какой). |
| `LoadCursorState(source, defaultState)` | Однократная загрузка состояния после готовности `GameManager` — из `ProjectPropertiesManager` либо из переданного `defaultState`, если сохранённого значения ещё нет. |
| `SetCursorSprite(sprite)` | Немедленная смена спрайта курсора в обход очереди запросов. |

`Show`/`Hide` с уже известным `source` не создают дубликат записи — они обновляют существующий запрос этого источника новым состоянием.

### Типичное использование

```csharp
public class SettingsWindow : MonoBehaviour
{
    private void OnEnable() => CursorManager.Instance.Show(this);
    private void OnDisable() => CursorManager.Instance.Release(this);
}
```

Если открыты `SettingsWindow` и, скажем, `InventoryWindow`, оба вызвавшие `Show`, а закрывается сперва `SettingsWindow` — `Release` увидит, что `InventoryWindow` всё ещё в списке активных запросов, и курсор останется видимым. Ни счётчик, ни стек в этом сценарии ничего не гарантируют без дополнительного кода — здесь это встроено в саму структуру данных.

## Внутреннее устройство

### Почему `List`, а не `Stack`

`activeRequests` — это `List<(object Source, CursorState State)>`, где порядок элементов — это порядок **последнего обращения**, а не порядок первого добавления. `SetRequest` при повторном обращении с уже известным `source` не обновляет запись на месте — она удаляется и добавляется заново в конец списка:

```csharp
private void SetRequest(object source, CursorState state)
{
    int index = activeRequests.FindIndex(r => Equals(r.Source, source));

    if (index >= 0)
        activeRequests.RemoveAt(index);

    activeRequests.Add((source, state));

    Apply(state);
}
```

Это важно для случая с тремя и более одновременными запросами. Пример: окно A открывается (`activeRequests = [A]`), окно B открывается (`[A, B]`), окно C открывается (`[A, B, C]`). Если после этого A обновляет своё состояние (например, переключение вкладки внутри самого A вызывает повторный `Show`), запись A перемещается в конец: `[B, C, A]`. Если теперь закрывается C — `Release` уберёт C и применит состояние **последнего оставшегося тронутого элемента**, то есть A (`[B, A]`, последний — A), а не B. Без переноса в конец при повторном обращении список остался бы `[B, C]` после снятия C, и `Release` вернул бы состояние B — то есть более старое взаимодействие "победило" бы более новое, хотя семантика метода (см. докстринг `Release`) обещает обратное.

### Play Mode без Domain Reload

Singleton-экземпляр (`SingletonProviderBase<CursorManager>.Instance`) — обычное статическое поле, которое ничем не сбрасывается между запусками Play Mode, если в Editor включена настройка **Project Settings → Editor → Enter Play Mode Settings → Reload Domain: выключено** (частая оптимизация для быстрого повторного входа в Play Mode). Без явного сброса `isLoadingState`, `activeRequests` и `defaultState` пережили бы предыдущую Play-сессию как есть, и повторный `LoadCursorState()` во второй сессии подряд молча ничего бы не сделал, потому что `isLoadingState` остался бы `true` с прошлого раза.

Поэтому в классе есть:

```csharp
[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]
private static void ResetOnLoad()
{
    Override(null);
}
```

`SubsystemRegistration` — самая ранняя стадия инициализации Unity, отрабатывающая перед загрузкой любой сцены, поэтому сброс происходит до того, как какой-либо код успевает закэшировать ссылку на старый экземпляр. Тот же паттерн уже используется в `Enumeration`/`EnumerationExtensions` для очистки их reflection-кэшей — здесь применён тот же приём для сброса состояния синглтона целиком через `Override(null)`, что заставляет следующий `Instance` создать свежий экземпляр (`Activator.CreateInstance<T>()` в `SingletonProviderBase<T>`).

## Сохранение состояния

`LoadCursorState(source, defaultState)` вызывается один раз (повторные вызовы до готовности `GameManager` игнорируются через `isLoadingState`) и, после `GameManager.ReadySignal`, либо восстанавливает сохранённое состояние через `ProjectPropertiesManager.Instance.TryGetValue(CursorStatePropertyName, out var value)`, либо применяет переданный `defaultState`, если сохранённого значения ещё нет.

`CursorStatePropertyName` — это `EnumerationType<bool>`, ключ для `ProjectPropertiesManager`. Класс сейчас только **читает** это значение при загрузке; если нужно ещё и **сохранять** состояние курсора (например, переключатель в настройках "показывать курсор"), запись делается напрямую через тот же ключ:

```csharp
ProjectPropertiesManager.Instance.SetValue(CursorManager.CursorStatePropertyName, isCursorVisible);
```

(Метод `SetValue<T>(EnumerationType<T>, T, ...)` в `ProjectPropertiesManager` появился именно ради таких случаев — раньше типизированный ключ можно было только читать.)

## Прямая смена спрайта

`SetCursorSprite(Sprite)` меняет системный спрайт курсора немедленно, в обход очереди запросов Show/Hide — не запоминается как часть `CursorState` и не восстанавливается через `Release`. Если понадобится спрайт, привязанный к конкретному запросу (например, разные курсоры для разных окон), предполагается добавить поле `Texture`/`Sprite` в `CursorState` и провести его через `Show`/`Hide`/`Release`, вместо того чтобы дергать `SetCursorSprite` отдельно и вручную синхронизировать его с состоянием запросов.

## История изменений

- Добавлена типобезопасная запись состояния через `EnumerationType<T>` в `ProjectPropertiesManager` (`SetValue`/`GetValue`/`AddLong`/`AddFloat`/`RemoveProperty`) — `CursorStatePropertyName` теперь можно не только читать, но и сохранять напрямую по ключу.
- `SetRequest` теперь переносит обновлённую запись в конец списка вместо обновления на месте — иначе порядок "кто трогал позже" мог разъезжаться с реальным порядком снятия запросов при трёх и более одновременных источниках.
- Добавлен `ResetOnLoad()` на `SubsystemRegistration` — синглтон корректно пересоздаётся при повторном входе в Play Mode с отключённым Domain Reload.
- Исправлена кодировка файла: был сохранён в Windows-1251, из-за чего все комментарии отображались как `�` в инструментах, ожидающих UTF-8 (в т.ч. потенциально в самом компиляторе C#, если он трактует файл без BOM как UTF-8 по умолчанию).

## Известные ограничения

- Класс не входит в статический фасад `PRUnitySDK` (`PRUnitySDK.Managers`/`.Windows`/...) — доступ только через `CursorManager.Instance`, аналогично `ProjectPropertiesManager` и `HookManager`.
- `Release` полагается на `Equals(object, object)` для сравнения `source` — если в качестве `source` передаётся не `this`, а, например, структура или объект с переопределённым `Equals`, стоит убедиться, что равенство ведёт себя ожидаемо (два разных логических источника не должны случайно оказаться "равны").
- Нет защиты от повторного `Release` одного и того же `source`, если он уже был снят (просто ничего не произойдёт, `FindIndex` вернёт -1) — это безопасно, но также не сообщает вызывающему коду, что запроса уже не было.
