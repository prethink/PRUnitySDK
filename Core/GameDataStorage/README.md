# GameDataStorage

Папка содержит контракты сохранения PRUnitySDK, реализации storage и общие адаптеры
для данных внутри `ProjectData`.

## Save metadata

`PRSaveData.SaveDate` хранит дату создания save, а `UpdateDate` обновляется непосредственно
перед каждой записью стандартными `PlayerPrefsSaveLoadManager` и `YandexGameDataStorager`.
Обе даты берутся из `PRUnitySDK.ServerTime`, поэтому используют единый настроенный источник времени.
Для старого save без `UpdateDate` стандартные storage используют `SaveDate` как fallback до следующей записи.

Storage может дополнительно реализовать `IGameDataStorageSaveInfo`, не расширяя обязательный
контракт `IGameDataStorage`. `GameManager` использует этот интерфейс, чтобы восстановить даты
создания и последнего обновления после перезапуска. Собственная реализация storage может вернуть `null`,
если метаданные недоступны.

## Версия сохранения

`PRSaveData.Version` хранит версию формата, в которой записано сохранение. Текущую версию
задаёт `GameStorageSettings.SaveVersion`, её ставит `SaveDataVersioning.Stamp` перед каждой
записью. Сохранения, записанные до появления версий, читаются как версия 0.

Поднимайте `SaveVersion`, когда меняется то, что лежит в сохранении. Что делать со старым
сохранением, решает `GameStorageSettings.VersionMismatchAction`:

| Действие | Что происходит |
| --- | --- |
| `Keep` (по умолчанию) | сохранение загружается как есть, без шагов: незнакомые поля пропускаются, недостающие остаются по умолчанию |
| `Convert` | сохранение проходит шаги `ISaveMigration` по версиям до текущей; если шаг бросил исключение, сохранение считается нечитаемым: игра идёт с новыми данными, запись до конца запуска выключена, сохранение игрока цело |
| `StartNew` | сохранение отбрасывается, начинается новое |

После `Keep` и `Convert` сохранение считается текущей версии и со следующей записью
получает её номер. Если позже переключить настройку на `Convert`, шаги для таких
сохранений уже не выполнятся.

Сохранение новее текущей версии загружается как есть при любой настройке, и его версия
при записи не понижается.

Отброшенное сохранение для `GameManager` выглядит как первый запуск: `TryLoad` возвращает
`false`, и данные заполняются значениями по умолчанию.

### Шаг преобразования

```csharp
public class RenameCoinMigration : ISaveMigration
{
    public int FromVersion => 1;

    public void Migrate(JObject save)
    {
        var resources = (JObject)save["ProjectData"]?["Resources"];
        if (resources?["Coin"] is JToken coins)
        {
            resources["Gold"] = coins;
            resources.Remove("Coin");
        }
    }
}
```

Шаг переводит ровно на одну версию, с `FromVersion` на `FromVersion + 1`. Версии без шага
сохранение проходит без изменений, поэтому поднять версию, ничего не меняя в данных, можно.
Шаги находятся автоматически, регистрировать их не нужно: в `link.xml` они попадают сами.
Нужен публичный конструктор без параметров.

Шаг работает с JSON до типизированного чтения. Поле, которое уже убрали из `ProjectData`,
в JSON ещё есть. Даты в нём остаются строками, как записаны, дробные числа читаются
в `decimal`.

Своё хранилище только переносит строку: читает через `SaveDataVersioning.TryReadRaw`,
пишет через `SaveDataVersioning.Serialize`. Шифрование, версия и отброшенное сохранение
обрабатываются там. Хранилище, которое держит сохранение объектом, читает через
`SaveDataVersioning.TryRead(PRSaveData, ...)` и перед записью вызывает `Stamp`. Чистую
логику без настроек проекта даёт `SaveDataVersioning.Upgrade`.

## Своё хранилище — от `GameDataStorageBase`

Хранилище, которое держит сохранение одной строкой, наследуется от `GameDataStorageBase` и пишет два метода:
`ReadRaw()` — отдать строку, `WriteRaw(string)` — принять её (вернуть `false`, если площадка не приняла).
Версия, шифрование, даты, копии данных для игры и сигнал готовности — в базе. Образец — `PlayerPrefsSaveLoadManager`;
на базе стоят и все хранилища площадок (YG2, GamePush, VK, Пикабу, Steam).

Хранилище, которое держит сохранение не строкой или в нескольких местах, переопределяет `ReadSave` / `WriteSave`:
Яндекс — для стратегии `Class`, Steam — чтобы выбрать более новую из двух копий (облако и диск).

Площадка при загрузке не поднялась — хранилище зовёт `MarkUnavailable()` из `ReadRaw`: игра начинается с нуля,
а запись до конца запуска выключена. Если площадка ответит позже, запись этого запуска не ляжет поверх настоящего
прогресса.

`LastSaveWritten` говорит, приняло ли хранилище последнюю запись. `GameManager` по нему решает, состоялось ли
сохранение: при выключенной или не принятой записи `SaveState` — `Failed`, событие `SaveGameEventArgs` не поднимается
(его ждёт списание покупок), а кулдаун всё равно отсчитывается.

Строка сохранения есть, но не прочиталась (не JSON, чужой ключ шифрования, оборванная запись) — база до конца
запуска не пишет: `IsWriteBlocked`. Игра идёт с новыми данными, как при первом запуске, а сохранение игрока остаётся
нетронутым. Без этого первая же запись заменяла его пустым. То же при исключении в шаге `ISaveMigration`: ошибка
в коде шага не должна стоить игроку прогресса, исправленная сборка прочитает сохранение снова. Пустая строка
и сохранение, намеренно отброшенное из-за версии (`StartNew`), записи не блокируют.

Запуск, не дождавшийся площадки (`Bootstrap.StartedWithoutPlatform`, сторож загрузчика), хранилище площадки не читает
и не пишет вовсе. Хранилище, которому площадка не нужна, отвечает `NeedsPlatform => false` (PlayerPrefs, Steam с его
диском).

Главные части сохранения — `ProjectData` и `GameSettings` — записаны не объектом (число, строка, массив): сохранение
нечитаемо, запись выключена. Поле с чужим типом **внутри** них сохранение нечитаемым не делает: чтение пропускает
ошибку поля, оно остаётся по умолчанию, остальное загружается. Со следующей записью прежнее значение этого поля
пропадает — тип поля в `ProjectData` меняют только шагом `ISaveMigration`.

Steam: файл на диске есть, но не открылся — запись в этом запуске выключена (что в файле, неизвестно); на диск
сохранение пишется через временный файл.

Различить «строки нет» и «не прочиталось» самому — `SaveDataVersioning.TryReadRaw(raw, out data, out unreadable)`.
Тесты — `GameDataStorageBaseTests`.

## ProjectDataMap

`ProjectDataMap<TKey, TValue>` предоставляет единый набор операций над выбранным
словарём текущего `ProjectData`:

- `TryGetValue` — чтение с различением отсутствующего ключа;
- `GetValue` — чтение с fallback без изменения данных;
- `GetOrCreateValue` — совместимое создание значения по умолчанию;
- `SetValue` — запись с информацией о предыдущем значении;
- `TryRemoveValue` — удаление с возвратом удалённого значения.

```csharp
var resources = new ProjectDataMap<string, long>(
    () => GameManager.Instance.GetProjectData(),
    data => data.Resources ??= new Dictionary<string, long>());

ValueChange<long> change = resources.SetValue("Coin", 100);
```

`ValueChange<T>` сообщает, существовал ли ключ, предыдущее и текущее значения, а также
был ли словарь фактически изменён.

`ProjectDataMap` не вызывает `SaveProjectData()` и не публикует события: это делает доменный фасад. Например, `ResourceManager` сохраняет данные и публикует `ResourceValueChangeEventArgs`, а `ProjectPropertiesManager` использует свои типизированные события.

Доступ к map требует уже загруженного `ProjectData`. Вызывающий runtime-сервис должен
ориентироваться на `GameManager.ReadySignal`.

### Кто использует

| Сервис | Словарь в `ProjectData` | Что решает сам |
| --- | --- | --- |
| [ResourceManager](../Items/Resources/README.md) | `Resources` | сохранение, `IResourceValueChangedEvent` |
| [ProjectPropertiesManager](../@Managers/ProjectPropertiesManager/README.md) | словари `ProjectProperties` по типам (`long`, `float`, `decimal`, `DateTime`, `string`, `bool`) | сохранение, типизированные события свойств |
| [TimeLimitedRewardService](../Reward/README.md#ограниченные-по-времени-награды) | `TimeLimitedRewards` | сохранение, события выдачи и истечения |

Заводить отдельный словарь стоит, когда данные образуют самостоятельный домен: их нужно
перечислять, чистить целиком или обрабатывать по своим правилам. Разовые значения без
такой потребности достаточно хранить в `ProjectProperties`.

## Настройки сохранения

`GameStorageSettings` (раздел `Game Storage` в окне `PRUnitySDK/Windows/Settings`) —
автосохранение и его период, стратегия записи, шифрование и его стратегия при загрузке.

Раздел реализует `IDefaultSettings`, поэтому у него в окне настроек работает кнопка
«Сбросить»: она зовёт `SetDefaultSettings` — тот же метод, которым заполняется новый
ассет настроек.

Стратегию записи и шифрование меняют до релиза: сохранения по прежним правилам после правки читаются уже не так, и игрок остаётся с файлом, который игра не понимает. Поэтому раздел помечен предупреждением в окне.

## PRGameStorageService

`PRGameStorageService` предоставляет именованные категории типизированных значений,
которые хранятся через `ProjectPropertiesManager`. Категория добавляется к ключу, чтобы
значения разных storage не пересекались.

Это фасад над произвольными свойствами, тогда как `ProjectDataMap` — низкоуровневый
адаптер для словарей конкретных доменных данных.

## Зависимости

| От чего зависит | Зачем |
| --- | --- |
| `IGameDataStorage` | конкретное хранилище: PlayerPrefs, облако площадки, своё |
| [GameManager](../@Managers/GameManager/README.md) | момент загрузки, сбор состояния и запись |
| `ServerTime` | даты создания и последней записи сохранения |

Кто зависит от него: всё, что хранит прогресс, — менеджеры ядра и модули проектного слоя.
Обратных ссылок нет: хранилище не знает, что именно в нём лежит.


## ISaveable

Часть состояния живёт не в `ProjectData`, а в самих объектах сцены: что стоит на площадке
и сколько она успела накопить. Такой объект перекладывает своё состояние в данные
проекта по запросу.

```csharp
public class SomeSceneObject : PRMonoBehaviour
{
    public override bool TrySaveData() { /* переложить состояние в ProjectData */ }
}
```

`TrySaveData()` вызывается перед каждой записью на диск — один раз для всех объектов — и ещё раз, когда объект уходит со сцены. Сбор синхронный: это перекладывание в память, а не работа с диском. Объект, вернувший `false` или бросивший исключение, не отменяет сохранение остальных — о нём пишется предупреждение в лог.

Порядок сбора — порядок появления объектов (`SaveableRegistry`): если двое пишут в одно
место, побеждает всегда один и тот же.

### Обратная сторона

Парного интерфейса нет: момент загрузки у каждого свой. Тот, кому нужно восстановиться, подписывается сам:

```csharp
GameManager.Instance.ReadySignal.SubscribeOnReady(() =>
{
    if (this != null)
        TryLoadData();
});
```

Ждать обязательно: хранилище отдаёт данные асинхронно, и на `Awake` в них пусто. Если сигнал уже поднят, подписка вызывается сразу, поэтому на синхронном хранилище ожидания не будет.

Всё, что и так лежит в `ProjectData` — кошелёк, открытые предметы, выбранная внешность, —
пишется туда сразу при изменении, и `ISaveable` ему не нужен.

## Готовый компонент состояния

Связку «применить значения по умолчанию → дождаться данных → применить сохранённое →
отдать состояние обратно» не нужно писать заново каждому объекту: её закрывает
`SaveableObjectState`. Он хранит активность объекта, а своё состояние наследники
добавляют через `CaptureState` и `ApplyState`.

Подробности, выбор ключа и подводные камни — в
[Состояние объекта сцены](ObjectState/README.md).
