# Editor-окна PRUnitySDK

Окна редактора PRUnitySDK: проверка проекта, Debug-окно для Play Mode, редакторы баз `PRSDKDatabase` и настроек `PRSDKSettings`.
Общие IMGUI helpers для собственных окон описаны отдельно в [ExtendedEditorWindow](ExtendedEditorWindow/README.md): toolbar и popup-меню, адаптивные вкладки, двухколоночный layout и работа с `SerializedProperty`.

## Проверка проекта

Окно `PRUnitySDK/Windows/Проверка проекта` проверяет ассеты в Edit Mode. Кнопка «Проверить» запускает все реализации `IProjectValidator`, кнопка «Исправить всё» применяет исправления к тем проблемам, у которых они есть.

Чтобы добавить свою проверку, положите рядом со своим модулем класс с конструктором без параметров, который реализует IProjectValidator. Окно найдёт его через TypeCache. Одна проблема описывается `ProjectValidationIssue`: уровень, текст, объект для кнопки «Показать» и необязательное действие исправления.

Проверки runtime-состояния находятся в другом окне — `Debug Window` и `IPRDebugHealthCheck`.

## PRUnitySDK Debug

Окно `PRUnitySDK/Windows/Debug Window` показывает runtime-диагностику в Play Mode.

Вкладка `Initialization` показывает успешно инициализированные модули, managers, core-singleton, зарегистрированные factories, MonoWindows, notifiers и другие типы в порядке запуска. Каждая категория — отдельная таблица с числом элементов и суммарным временем. В записи видны фактический тип реализации, затем тип контракта и время операции. Сверху — суммарное отслеживаемое время. Колонка `Name` скрыта, но имя участвует в общем поиске. Кнопка `Source` выбирает и подсвечивает в Project/Inspector скрипт фактической реализации; если его нет, выбирается скрипт контракта.

Вкладка `Problems` запускает автоматически обнаруженные реализации `IPRDebugHealthCheck` и собирает найденные проблемы в одну таблицу с уровнями `Info`, `Warning` и `Error`. Встроенная проверка диагностирует незавершённую инициализацию, несовместимость contract/implementation, отсутствующие managers и контейнеры, повторяющиеся Entity ID, конфликт состояний scene/pool, расхождение счётчиков pools и некорректное состояние MonoWindows. Ошибка одной проверки показывается как отдельная проблема и не прерывает остальные. `Object` выбирает связанный runtime-объект, `Source` открывает скрипт типа, отвечающего за проблему.

Вкладка `Object states` показывает объекты, чьё состояние переживает перезапуск: группу, ключ, состояние на сцене и запись в сохранении. Сверху — сводка «показано N из M». Записи без объекта текущей сцены считаются отдельно: это прогресс других уровней или мусор от удалённых объектов. Подробности — в [Состояние объекта сцены](../GameDataStorage/ObjectState/README.md).

Вкладка `Saves` показывает, что лежит в сохранении: свойства проекта по типам (`long`, `float`, `decimal`, `bool`, `string`, `DateTime`, `object`), ресурсы, сроки временных наград и размеры списков — открытых предметов и выбранного у игроков. Значения берутся из `ProjectData` в памяти, а не с диска, поэтому видно и то, что ещё не записано. Кнопка `Сохранить сейчас` пишет данные, не дожидаясь кулдауна.

Изменения ловятся сравнением с прошлым обновлением окна. Строка показывает прежнее значение и время с изменения; новое значение подсвечивается первые пять секунд. Точность равна интервалу обновления: два изменения внутри одного интервала сливаются в одно. Появившийся ключ помечается как `<появилось>`.

`Только изменённые` оставляет строки, которые менялись с открытия окна или с последнего `Забыть изменения`. Исчезнувшие ключи не убираются: запись «было столько» — единственный след удалённого свойства.

Под заголовком каждой вкладки стоит короткое описание: без него часть цифр читается неверно.

Чтобы добавить проектную проверку, создайте Editor-only конкретный класс с конструктором без параметров:

```csharp
public sealed class ExampleHealthCheck : IPRDebugHealthCheck
{
    public IEnumerable<PRDebugProblem> Check()
    {
        if (ExampleService.Instance == null)
        {
            yield return new PRDebugProblem(
                PRDebugProblemSeverity.Error,
                "Example",
                "MissingService",
                "ExampleService is not initialized.",
                sourceType: typeof(ExampleService));
        }
    }
}
```

Регистрировать проверку в Debug-окне не нужно: Editor находит наследников через `TypeCache` после domain reload.

Вкладка `Windows` показывает зарегистрированные `MonoWindowBase`: фактический тип, key, `Visible`, активность GameObject и признак `CurrentWindow`. Окно и его скрипт можно выбрать. Видимое окно можно принудительно закрыть без сохранения, скрытое — открыть с `MonoWindowArgsEmpty`. Окна с обязательными типизированными args следует открывать обычным игровым способом.

В шапке выбирается исполнитель: его идентификатор уходит в `MonoWindowArgs.Executor`. По нему окна находят своего игрока: кастомизация понимает, кому надеть вещь. `Auto` оставляет ноль, и окно решает само. С одним игроком этого достаточно; в сплит-скрине без выбора всё достаётся первому. Выбор общий для окна и переживает domain reload. Тот же игрок назначается кнопкой `Use` во вкладке `Players`.

Вкладка `Tasks` показывает зарегистрированные фоновые задачи, обычные и живущие на объектах сцены: ключ, тип, состояние, интервал, обратный отсчёт до следующего запуска, время с последнего, счётчики выполнений, пропусков и ошибок, длительность последнего запуска. Для задач-наблюдателей (любой реализации `IWatcherTask<T>`) в колонке `Value` выводится прочитанное значение. Статус подсвечивается: `Faulted` красным, `Paused` жёлтым, `Completed` синим. Рядом со счётчиком показывается число ошибок подряд. Последняя ошибка выводится строкой под задачей.

Кнопка `Object` активна только у задач-компонентов (`BackgroundTaskBehaviour`) и выбирает их GameObject; у обычных задач она пустая. `Source` открывает скрипт задачи в обоих случаях.

Кнопка `Run` выполняет задачу немедленно **в обход `CanExecute()`**. `Pause` и `Resume` управляют выполнением. `Reset` снимает признак отказа и сбрасывает счётчик запусков — им возвращают в работу задачу в состоянии `Faulted` или `Completed`. Обратный отсчёт задач, работающих по игровому времени, замирает вместе с логической паузой. Подробности модели — в [BackgroundTasks](../BackgroundTasks/README.md).

Вкладка `Rules` показывает загруженные правила характеристик из `GameRules`: характеристику, номер в порядке применения, тип правила, приоритет и собственные параметры правила. Параметры берутся рефлексией из свойств, объявленных в самом типе, поэтому новые виды правил попадают в таблицу без правок редактора. Правила одной характеристики идут подряд в порядке применения: по возрастанию `Priority`, при равенстве — по порядку объявления в провайдере. У второго и следующих правил имя характеристики приглушено, а колонка `#` содержит номер правила в цепочке.

Сверху — блок `Apply rules to value`: выберите характеристику, введите значение и увидите результат `GameRules.ApplyStatRules`. Если правила изменили число, результат подсвечивается и появляется пометка `value was clamped`. Так видно, какое ограничение срезает значение, без запуска геймплея. Подробности — в [GameRules](../GameRules/README.md).

Вкладка `Metrics` показывает последние 200 вызовов адаптеров метрик: время UTC, имя события, тип адаптера и параметры после нормализации. Параметры раскрываются и копируются вместе с событием. Общий поиск работает по имени, адаптеру и JSON. `Capture` останавливает запись, `Clear` очищает журнал.

Запись идёт с начала Play Mode даже при закрытом Debug-окне. После остановки игры журнал виден среди доступных в Edit Mode разделов; новый запуск очищает его. `DummyMetric` отмечен как Ignored, остальные записи — Sent: вызов передан адаптеру, подтверждения доставки сервером у синхронного API нет. Диагностика собирается только в Editor и не входит в сборку. Подробнее — [Metrics](../Metrics/README.md).

Вкладка `Events` записывает последние 200 обычных вызовов `EventBus`, пока Debug-окно открыто и включён `Capture`. Покадровые `IOnUpdateEvent` и `IOnPRUpdateEvent` выводятся отдельной агрегированной таблицей: общее число вызовов, средняя частота, число подписчиков и время последнего вызова. Список таких типов задан в `PRDebugEditor.AggregatedEventTypes`; другие покадровые интерфейсы можно добавить туда без изменения EventBus. Payload не сохраняется. Историю можно поставить на паузу и очистить.

Над монитором находится блок `Raise events` с кнопкой `Restore hidden entities`: она поднимает `IRestoreHideEntitiesEvent` и возвращает на сцену сущности с настройкой `EntityDisposeAction = Hide`, заново их инициализируя. Рядом показано число живых подписчиков.

Вкладка `Entities` показывает статистику по типам и каждый зарегистрированный экземпляр. Оба списка занимают по половине высоты окна и прокручиваются отдельно: тип выбирают в верхнем, экземпляры смотрят в нижнем.

Строка типа раскрывается по видам предметов. Вид берётся из `Info` определения, поэтому колонка `Registered` у вида показывает число живых экземпляров этого вида. Трекер ведёт счёт только по типу. Поиск по имени вида раскрывает нужный тип автоматически.

Вид `<no info>` значит, что у сущности нет определения. Обычно так бывает с префабом, общим для нескольких предметов. Такие сущности видны по типу и числу, но не по имени и иконке.

`Select` выбирает GameObject экземпляра в Hierarchy/Inspector. `Dispose` после подтверждения вызывает `IEntity.DestroyEntity()` и соблюдает `EntityDisposeAction`: сущность может быть полностью уничтожена либо возвращена в pool. Колонка `Pool` различает неподключённый объект (`No`), активный объект зарегистрированного пула (`Ready`) и уже возвращённый объект (`In pool`). Для `In pool` повторный `Dispose` недоступен. `EntityBase` тоже игнорирует повторный обычный dispose; явное удаление возможно через `FullDestroy = true`.

Вкладка `Pools` позволяет очистить отдельный пул или все пулы после подтверждения. Очистка останавливает корутины создания и времени жизни, уничтожает свободные и активные `GameObject` и удаляет регистрацию пула. Перед следующим использованием пул нужно зарегистрировать заново.

Вкладка `Flags` автоматически находит конкретных наследников `FlagsProviderBase`, включая проектные типы вроде `PlayerFlags`. В блоке `Global test flags` можно выбрать provider и flag, добавить для него тестовое `Allow` или `Deny`, удалить выбранное влияние или очистить все тестовые влияния. Изменения применяются только к project-wide `FlagsManager.Global`, используют отдельный source Debug-окна и автоматически снимаются при закрытии окна или перезагрузке scripts.

Вкладок больше десятка, поэтому раздел выбирается выпадающим списком. Ширина списка подбирается по самой длинной подписи, и счётчики видны целиком.

Окно поддерживает узкую docked-вкладку рядом с Inspector. При ширине меньше `620 px` верхняя панель переходит в компактный двухстрочный режим, а таблицы прокручиваются по горизонтали. `Summary` на вкладке `Overview` выводится компактными строками `Label: Value`: при обычной ширине числовые показатели помещаются в один ряд, в узком окне строки переносятся на две или четыре колонки. Горизонтальная полоса остаётся только на табличных вкладках. В развёрнутом окне основная область ограничена `1000 px` и центрируется.

Секция `Save Info` на `Overview` показывает, был ли загружен существующий save, состояние записи, локальные даты создания и последнего обновления и оставшийся cooldown. Кнопка `Save` запускает обычный `GameManager.StartSaveTask()`. Она доступна только после истечения `GameStorage.SaveCooldownSeconds` и не работает во время сохранения.

Секция `PRTimeScale` показывает combine mode, число подписчиков `IOnPRTimeScaleChange` и все слои из `PRTimeScaleEnumerationProvider`: собственное значение слоя и итоговый результат `Resolve`. Постоянное значение каждого слоя можно изменить числом. Блок временного global override принимает scale и длительность в реальных секундах. Presets `0`, `0.25`, `0.5`, `1`, `2` заполняют scale, а `Apply` вызывает `SetGlobalTimeScaleTemporarily`. Повторное применение недоступно до автоматического восстановления. Debug-окно использует только публичные методы `PRTimeScale` и не изменяет `UnityEngine.Time.timeScale`.

Секция `Language` на `Overview` показывает текущий языковой код и фактический тип зарегистрированного `ILanguageManager`. Выпадающий список переключает русский, английский и турецкий через активную реализацию менеджера, поэтому platform override (например, `YGLanguageManager`) не обходится.

Секция `Cursor` там же показывает `Cursor.visible`, режим блокировки и наличие запроса от окна. Кнопки `Show`, `Hide` и `Release` управляют курсором через `CursorManager`, как обычный источник запроса. Запрос снимается кнопкой `Release`, при закрытии окна и при перезагрузке скриптов.

## PRSDKDatabase и PRSDKSettings

Assets `PRSDKDatabase` и `PRSDKSettings` редактируются в отдельных растягиваемых `EditorWindow`. Обычный Unity Inspector при этом не переопределяется. Окна показывают поля, добавленные к singleton-классам через partial, поэтому при подключении нового модуля Editor менять не нужно.

Оба окна поддерживают:

- поиск секции по названию;
- сворачивание и разворачивание секций;
- сохранение изменённых assets;
- растягивание вложенных списков и настроек на доступную ширину Inspector.

Публичный SDK использует только стандартный Unity Editor API и не зависит от инспекторов или атрибутов private SDK.

Окна открываются через меню `PRUnitySDK/Windows/*`. Кнопка `Asset` выбирает редактируемый asset в обычном Unity Inspector.

## PRSDKDatabase

Каждая секция раскрывается независимо от остальных. Развёрнутый каталог использует ширину окна и получает высоту относительно текущего размера окна. Если `Database<T>` находится внутри другого сериализуемого объекта, редактор показывает его отдельной вложенной секцией.

Для каждой секции, наследующейся от `Database<T>`, где `T` является Unity asset, автоматически появляются дополнительные операции:

- `Добавить все` — находит в `Assets` все совместимые definitions и добавляет только отсутствующие ссылки;
- `Убрать null` — удаляет повреждённые пустые элементы;
- `Очистить` — очищает секцию после подтверждения, не удаляя сами asset-файлы.

Карточки в сетке выделяются как в Project: обычный щелчок выделяет одну, `Ctrl` (`Cmd`) — добавляет или убирает по одной, `Shift` — диапазон от последней отмеченной. `Delete` убирает выделенное из каталога, как кнопка `Удалить из базы`; при групповом выделении кнопка показывает число элементов. `Backspace` окно не занимает: им стирают символы в полях карточки.

Пока правится значение в панели свойств, клавиша принадлежит полю: `Delete` очищает `Scale Factor`, а не удаляет предмет из каталога.

Клавиша спрашивает подтверждение всегда, даже об одной карточке, и называет её по имени. Кнопка спрашивает подтверждение только для группы. Сами ассеты остаются в проекте.

Кнопка `Наборы` сохраняет и загружает состав каталогов. Набор влияет на размер билда. Загрузка идёт в два шага; отчёт показывает, что из набора не сошлось с проектом. Подробности — в [DATABASE-PRESETS.md](DATABASE-PRESETS.md).

Набор охватывает **только разделы своего окна**: набор, снятый в «Предметах», описывает предметы и применяется к ним же. Окно правит только то, что показывает. Разделы набора, не относящиеся к окну, пропускаются с пометкой в отчёте. Имя файла по умолчанию содержит имя окна.

`Database<T>.Validate()` по умолчанию проверяет пустые элементы, дубликаты элементов, пустые и повторяющиеся стабильные `Id`. Конкретная база может дополнить правила:

```csharp
[Serializable]
public sealed class ExampleDatabase : Database<ExampleDefinition>
{
    public override IEnumerable<DatabaseValidationIssue> Validate()
    {
        foreach (DatabaseValidationIssue issue in base.Validate())
            yield return issue;

        foreach (ExampleDefinition definition in Data)
        {
            if (definition != null && definition.Icon == null)
            {
                yield return new DatabaseValidationIssue(
                    "missing-icon",
                    $"У '{definition.name}' отсутствует иконка.",
                    DatabaseValidationSeverity.Warning);
            }
        }
    }
}
```

Каталоги проектного слоя дополняют общую проверку: имя, иконка, переводы, prefab, а где нужно — значения вроде отрицательного дохода или стоимости.

### Разделы со своим окном

Каталогу, переросшему общий список, можно выдать собственный редактор: пометьте его класс атрибутом `DatabaseExternalEditor` с путём пункта меню.

Окна SDK разложены по этому же правилу:

| Окно | Меню | Что показывает |
| --- | --- | --- |
| Общее | `PRUnitySDK/Windows/Common` | действия, спрайты, звуки |
| Предметы | `PRUnitySDK/Windows/Items` | каталоги вещей, наборы, брейнроты, питомцы |
| Награды | `PRUnitySDK/Windows/Rewards` | контейнеры подарков и кейсов, все награды проекта, генератор |
| Витрина | `PRUnitySDK/Windows/Shop` | товары, цены и условия покупки |
| Переводы | `PRUnitySDK/Windows/Localization` | списки по языкам и таблица проекта |
| Достижения | `PRUnitySDK/Windows/Achievements` | условия, прогресс и награды |

Окно **кнопок HUD** (`PRUnitySDK/Windows/Buttons`) находит все `UIButtonDefinition` проекта. Слева — карточки с превью трёх слоёв, поиск по имени, пути, ключу и переводам и фильтр по типу. Справа — обычный инспектор кнопки с проверками заполнения. Из окна можно создать кнопку, сохранить выбранный ассет и показать его в Project. Те же три слоя рисуются и картинкой самого ассета — в окне выбора и в Project (`UIButtonDefinitionEditor.RenderStaticPreview`); после смены иконки ассет нужно переимпортировать.

Окно **описаний сущностей** (`PRUnitySDK/Windows/Entity metadata`) не наследует `PRSDKDatabaseEditor` и не привязано к разделу базы. Ассеты описаний и определений ищутся по проекту, каталога для них нет. Вкладок три: описания (`EntityMetadataBase`), определения (`ItemDefinitionBase`) и проверка — сводка проблем по всему проекту.

На вкладке описаний есть фильтр «Тип сущности» по `EntityType`: например, `Weapon`, `Projectile`, `Prop`, `Common`. Список типов собирается из найденных метаданных и работает вместе с поиском и фильтром класса ассета. «Все типы» снимает ограничение. Выбранное значение сохраняется по ключу при обновлении списка и перекомпиляции; если тип исчез, фильтр сбрасывается.

У выбранного ассета видно, **кто им пользуется**: сетка префабов с превью и список сцен. У Unity нет обратной связи «ассет → кто на него ссылается», поэтому список собирается обходом зависимостей и сбрасывается при импорте. Открытые сцены просматриваются вживую: объект, добавленный в сцену, виден до её сохранения.

Блок «Префабы» реализован через `IDatabaseAssetInspector`, поэтому появляется и в обычных окнах каталогов — у любого `ItemDefinitionBase`.

Специализированные окна — наследники `PRSDKDatabaseEditor` с одним переопределением: `OwnedEditorMenuPath` возвращает их путь меню. Разметка, сетка, поиск, проверки, наборы состава и удаление достаются им как есть — писать второй редактор не нужно.

```csharp
public sealed class PRSDKItemsWindow : PRSDKDatabaseEditor
{
    public const string MenuPath = "PRUnitySDK/Windows/Items";

    protected override string OwnedEditorMenuPath => MenuPath;
}
```

Связь окна с разделом — через тот же путь меню в атрибуте: своё окно рисует раздел полностью, общая база показывает ссылку, чужие специализированные окна не показывают вовсе.

```csharp
[DatabaseExternalEditor(
    "PRUnitySDK/Windows/Localization",
    WindowName = "Localization",
    Description = "Переводы правятся там: списки по языкам, проверки и обмен таблицей.")]
public class LocalizationDatabase
```

В окне базы такой раздел не редактируется: остаётся строка с названием, пояснением и кнопкой, открывающей нужное окно.

Так помечены переводы и достижения.

### Видимость действий

Кнопки и результаты проверки управляются атрибутом на классе базы:

```csharp
[DatabaseEditorOptions(
    ShowAddAll = true,
    ShowRemoveNull = true,
    ShowClear = false,
    ShowValidation = true)]
[Serializable]
public sealed class ExampleDatabase : Database<ExampleDefinition>
{
}
```

Если атрибут отсутствует, все поддерживаемые действия включены. `Добавить все` и `Убрать null` появляются только для коллекций Unity assets; для обычных сериализуемых значений остаются список и базовая валидация.

### Представление ItemDefinition

Базы наследников `ItemDefinitionBase` в режиме `Auto` отображаются как каталог:

- слева — карточки с `IIconProvider.Icon` и `INameProvider.Name`;
- выбранная карточка подсвечивается цветом `IQualityProvider.Quality`, если качество доступно;
- справа стандартный встроенный редактор показывает все сериализованные поля выбранного asset без подключения стороннего custom inspector;
- границу между каталогом и свойствами можно перетаскивать; обе панели прокручиваются независимо и занимают всю высоту окна;
- карточки можно сортировать по качеству, имени или дате добавления, фильтровать по качеству и оставлять только элементы с проблемами валидации;
- отдельный definition можно добавить через ObjectField над сеткой или удалить кнопкой в правой панели.

Сортировка по дате добавления использует позицию элемента в сериализованном списке базы. Кнопка со стрелкой переключает направление сортировки. Сортировка влияет только на карточки в Editor и не переставляет элементы в самой базе.

Фильтр `Только с ошибками` использует `DatabaseValidationIssue.Index`: валидатор должен указывать индекс проблемного элемента. Ошибки с индексом `-1` относятся ко всей базе и карточке не соответствуют.

Для `SerializedCollections` правая панель использует `SerializedDictionaryInstanceDrawer`, поэтому словарь выглядит как в обычном Inspector. Файлы стороннего плагина не изменяются.

Для остальных полей используется обычный `EditorGUILayout.PropertyField`: Unity сохраняет существующие `PropertyDrawer`, например `SpritePreviewDrawer`, `PrefabPreviewDrawer`, drawer ссылок `Enumeration` и стандартные отображения массивов, объектов, enum и ссылок. Результат соответствует обычному Inspector. Публичное окно не зависит от private `NaughtyInspector`.

Представление можно установить явно:

```csharp
[DatabaseEditorOptions(Presentation = DatabaseEditorPresentation.Grid)]
public sealed class ItemDatabase : Database<MyItemDefinition>
{
}
```

`DatabaseEditorPresentation.Default` возвращает обычный список, а `Auto` выбирает сетку для любого наследника `ItemDefinitionBase`. Каталог может выбрать `Grid` и явно.

Список по-прежнему можно редактировать вручную. Поэтому конкретный проект может держать в базе только нужные definitions и не включать остальные ссылки в конфигурацию перед сборкой.

Очистка ссылки в базе сама по себе не удаляет asset и не гарантирует его исключение из билда: Unity всё равно включит definition, если на него ссылается сцена, prefab, другой включённый asset либо он находится в `Resources`.

## PRSDKSettings

Каждое сериализованное partial-поле показывается отдельной секцией. Например, `Advertising`, `Rating`, `Quality` или настройки нового модуля автоматически появятся в инспекторе после добавления поля в `PRSDKSettings`.

У секции есть собственная шапка: заголовок-foldout и кнопка `Сбросить` справа от него.

### Описание секции

Описание есть у всех сорока разделов и подразделов настроек.

Над полями развёрнутой секции показывается её описание из атрибута на классе раздела:

```csharp
[SettingsDescription("Качества предметов: вес в случайной выдаче, цвет подписи и поправка к уровню.",
    Warning = "Вес — не проценты: шанс считается долей от суммы весов.")]
public class PRQualitySettings
```

Описание задаётся в атрибуте на классе раздела, а не в окне. `Tooltip` поля отвечает на вопрос «что делает эта галка», описание — «зачем сюда вообще заходить», поэтому одно другое не заменяет. Необязательный `Warning` рисуется отдельной жёлтой пометкой.

Описание показывается только у развёрнутой секции.

### Подсветка включённых

Заголовок раздела с флагом включения подсвечивается зелёным, пока флаг поднят. Флаг — поле с именем `Enabled`, `IsEnabled`, `Active` или `IsActive`. Список имён закрытый: поле вроде `ShowNames` не учитывается. Выключенные разделы не подсвечиваются.

### Вложенные разделы

Описание и кнопка сброса есть не только у разделов верхнего уровня. Поле, чей тип помечен `SettingsDescription`, окно рисует таким же разделом — со своим foldout, описанием и сбросом. Так устроены подразделы опыта: `Bar`, `Popup`, `Pickup`, `Background`, `Booster`.

Поля без такого атрибута рисуются обычным `PropertyField` вместе со своими PropertyDrawer-ами, вложенными списками и разметкой.

Сброс вложенного раздела работает так же, но правку получает поле внутри родительского раздела; в `Undo` и в «грязные» при этом попадает сам ассет настроек.

### Сброс секции

Кнопка `Сбросить` спрашивает подтверждение и пишется в `Undo`. Что именно она делает, зависит от раздела:

| Раздел | Что происходит |
| --- | --- |
| реализует `IDefaultSettings` | вызывается его `SetDefaultSettings` — тот же метод, которым заполняется новый ассет настроек |
| обычный | раздел собирается заново: поля возвращаются к значениям из объявления, ссылки на ассеты внутри раздела очищаются |

Диалог называет два случая разными словами. Если значения по умолчанию раздела отличаются от инициализаторов полей, реализуйте `IDefaultSettings`: кнопка начнёт вызывать ваш метод.

После сброса окно прекращает отрисовку кадра; следующий кадр рисует новые значения.
