# Наборы базы данных

Сохраняют и загружают **состав** каталогов `PRSDKDatabase` — какие определения входят
в сборку конкретной игры.

Один проект SDK обслуживает несколько игр, и набор доступных шапок, очков, эффектов
у них разный. Это прямо влияет на размер билда: всё, на что ссылается база, попадает
в сборку. Набор позволяет переключать состав целиком, а не собирать его заново руками.

## Как пользоваться

Окно `PRUnitySDK Database` → кнопка **Наборы**:

- **Сохранить набор…** — снимает текущий состав всех каталогов в JSON.
- **Загрузить набор…** — читает файл и показывает отчёт. База меняется только после
  кнопки `Применить`.

## Два режима применения

| Режим | Что делает |
| --- | --- |
| **Заменить состав** | каталоги становятся ровно такими, как в наборе; лишнее уходит |
| **Дополнить** | существующее остаётся, из набора добавляется недостающее |

Замена — основной режим переключения между играми: состав должен быть ровно тем, что
задумано, иначе в билд утечёт лишнее. Дополнение нужно, когда набор — не полный состав
игры, а добавка: например, общий пакет предметов поверх уже собранной базы.

При дополнении существующее идёт первым и сохраняет порядок, а каталог, в который ничего
не добавилось, не трогается вовсе.

Режим выбирается прямо в отчёте, и цифры пересчитываются под него: одно и то же
«элементов вне набора» при замене означает потерю, а при дополнении — что они останутся.

По умолчанию файлы кладутся в `DatabasePresets/` рядом с `Assets`. Это не папка проекта
Unity: набор нужен только редактору, импортировать его как ассет незачем, а git его
всё равно видит.

## Что сохраняется

Каталогом считается любой массив ссылок на ассеты внутри базы — по форме, а не по типу.
Так под правило попадают и `Database<T>`, и разделы вроде оружия, где несколько списков
лежат рядом.

Каждый элемент записывается тремя способами:

| Поле | Зачем |
| --- | --- |
| `guid` + `localId` | основной способ: переживает переименование и перемещение файла |
| `path` | запасной: если GUID не совпал |
| `name` + `type` | последний: если и пути нет |

Три способа нужны потому, что набор приезжает из другой игры или ветки. Ассеты,
скопированные между проектами без `.meta`, получают новые GUID, и без запасного поиска
набор пришлось бы собирать заново.

Пустые ссылки не сохраняются: набор описывает состав, а дырка в списке — дефект текущей
базы, и переносить его в другую игру незачем.

## Проверка при загрузке

Загрузка идёт в два шага: сначала сверка, потом изменение. Отчёт показывает, сколько
записей встанет в базу, и перечисляет находки.

| Находка | Что значит |
| --- | --- |
| Ассет не найден | ни по GUID, ни по пути, ни по имени — запись пропущена |
| Найден по пути | GUID не совпал; вероятно, копия из другого проекта — стоит проверить |
| Тип не тот | ассет с таким GUID существует, но каталогу нужен другой тип — пропущен |
| Элементы вне набора | сейчас в базе есть, в наборе нет — при применении уйдут |
| Каталога нет в базе | набор старше SDK — раздел пропущен |
| Каталог сменил тип | раздел пропущен целиком |
| Дубликат | элемент указан в наборе дважды — лишний пропущен |
| Каталога нет в наборе | останется без изменений |

Две последние строки — про разное, и это важно.

**Каталога нет в наборе** — раздел не трогается вовсе. Набор может быть старше базы,
и вычищать раздел, о котором он ничего не знает, нельзя.

**Элементы вне набора** — раздел в наборе есть, но состав разошёлся: после сохранения
в базу добавили предметы. Что с ними будет, решает режим. Отчёт называет их поимённо
(первые шесть), а диалог подтверждения пересчитывает по всем каталогам. Сами ассеты
остаются в проекте в любом случае — набор описывает состав, а не содержимое.

Если применить всё же нечего, кнопка `Применить` выключается. Когда часть записей
не разрешилась, диалог подтверждения говорит об этом прямо.

## Что будет, если база изменится

| Изменение | Поведение |
| --- | --- |
| В проект добавили новые определения | набор о них не знает; в базу они не попадут |
| В базу добавили предметы после сохранения набора | сообщение «элементы вне набора»: при замене уйдут, при дополнении останутся |
| В SDK появился новый каталог | «каталога нет в наборе» — остаётся как есть |
| Каталог убрали из SDK | «каталога больше нет в базе» — раздел набора пропущен |
| Каталог переименовали | старый раздел пропущен, новый остаётся как есть — состав придётся перенести руками |
| Определение удалили из проекта | «не найден» — запись пропущена |

## Ограничения

- Набор хранит состав, а не сами определения. Ассетов, которых в проекте нет, он
  не создаст — только сообщит, что их не хватает.
- Порядок элементов сохраняется, но сортировка в окне на него не влияет.
- Проверка типа идёт по имени класса, а не по полному имени с namespace: два одноимённых
  типа в разных namespace она не различит.
